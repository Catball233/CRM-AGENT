# 装修行业“销冠”销售智能体｜需求分析与立项简报

> 文档角色：立项与需求演进归档，不是当前产品需求的唯一事实来源。当前状态、冻结候选和正式范围请从 [项目文档索引](../00-项目文档索引.md) 进入。

## 0. 当前结论：产品范围已明确，待补齐真实业务数据后进入实现

MVP 的业务边界、功能优先级、知识内容结构、报价安全架构和 KPI 已形成默认方案。进入开发前仍需由装修公司提供真实城市、材料／施工／设计师价格、成本与利润边界，并确认数据治理责任人。正式报价规则由受控知识库内容生成，经校验审批后发布为 RDS／规则引擎中的版本化运行规则。

## 1. 项目定位

| 项目 | 已确认内容 |
| --- | --- |
| 默认行业 | 装修 |
| 服务对象 | B 端装修企业主及其销售／客服团队 |
| 核心问题 | 客服维护成本高、客户与会话数据录入依赖人工、跟进不可自动化、销售过程难追踪且难管理 |
| 产品目标 | 用销售智能体优化客户咨询、需求收集、报价与跟进环节，降低重复沟通与漏跟进 |
| 行业适配理由 | 装修高度客制化，报价受多变量与地区差异影响，客户互动频繁，报价场景能体现智能销售价值 |

## 2. 目标用户与核心场景

**主要用户**：装修企业主、销售主管、客服／销售人员。

**客户侧主路径**：

```text
客户咨询 → 识别意图与需求 → 收集报价条件 → 规则校验 → 生成方案／报价
       → 识别意向与异议 → 跟进或转人工 → 记录客户与会话
```

本流程可以标准化为“信息收集—规则计算—对话引导—人工兜底”。方案设计、最终成交和特殊折扣仍应保留人工决策空间。

### 2.1 默认业务边界与地区规则

- 默认面向一家单城市经营的住宅装修公司，服务个人住宅业主。
- 支持毛坯新房、已交付新房和旧房翻新；支持全屋装修、局部装修、仅设计及设计施工一体化。
- 定制家具、软装和智能家居作为附加项目，不作为首期独立主营业务。
- 默认不承接商业／公共工程，不提供正式合同、在线支付、施工排期和许可审批服务。
- 地区分为核心服务区、灰度服务区和不承接区：核心区正常预估报价；灰度区生成条件性报价并强制人工确认；不承接区不生成具体价格。
- 正式城市与行政区清单在上线前通过知识库配置，不在代码中写死。

## 3. MVP 范围与优先级

| 优先级 | 能力 | MVP 说明 |
| --- | --- | --- |
| P0 | 客户聊天网页与会话 | 匿名客户可咨询、查看流式回复、提交联系方式，并维持安全会话。 |
| P0 | 用户意图识别 | 每条消息识别意图、购买相关性和回复策略；增加投诉／售后、违规内容、竞品比较、提示词注入、敏感信息和连续识别失败。 |
| P0 | 报价规则判断 | 依据规则检查面积、预算、设计／材料／套餐偏好、采购与安装方式等条件；信息不全时按优先级追问，而非直接报价。 |
| P0 | 预估价格计算 | 正式规则由知识库内容生成并发布为版本化运行规则；模型只输出 `rule_id + 参数 + 方案`，服务端读取已发布规则计算。 |
| P0 | 知识库问答 | 回答公司、工艺、材料、套餐、服务流程、案例与常见问题；回答应给出可追溯的知识来源或“信息不足”提示。 |
| P0 | 用户意向分析与跟进建议 | 输出高／中／低／未知意向、原文证据、关注点／顾虑、建议动作和跟进时间；不得无证据推断或自动执行外部联系。 |
| P0 | 基础人工兜底 | 客户主动请求、投诉、无可靠规则、规则冲突或地区不明时停止自动报价，收集联系方式并生成交接摘要。 |
| P1 | 实时销售工作台 | 销售在线状态、实时消息、排队认领、交还 AI、关闭会话和浏览器通知。 |
| P1 | 完整回访与报价比较 | 回访任务、报价版本差异、降配／升级方案和运营统计。 |
| P2（可选） | 文档本地化与向量化 | 导入 PDF、Word、图片等企业资料到知识库。 |
| P2（可选） | 历史记录、客户数据与记忆 | 保存会话、客户资料、长期摘要与短期上下文。建议作为 P1/P2 基础能力预留数据模型。 |
| P2（可选） | 语音与音色回复 | 将批准的文本回复转语音发送。 |

> P0 是首期上线闭环；P1 是已接受的 MVP 增强范围，可在 P0 稳定后迭代；P2 不阻塞 MVP。详细内容顺序见《装修销售 AI 知识库内容需求索引》。

## 4. 报价规则：已知变量与设计约束

### 4.1 当前已知变量

- 面积／平数、客户预算；
- 设计师等级、经验或资质；
- 材料与套餐档次（低／中／高配）；
- 客户自购、企业代购、企业安装等采购／履约方式；
- 材料费、安装费、设计费、服务费；
- 成本、最低利润、最低可成交价、折扣与套餐规则。

### 4.2 必须遵循的规则

- 报价知识由业务人员按标准模板维护，是正式规则的内容来源；知识库内容经自动校验和报价负责人审批后发布到 RDS／规则引擎。
- 大模型只做语义理解、字段抽取、缺失追问、方案解释与候选 `rule_id` 选择；金额由服务端读取已发布规则版本计算。
- 知识检索用于找到规则说明与证据，检索切片不能直接充当运行时计算公式。
- 没有满足报价条件时，系统必须说明缺少什么并继续收集，而非猜测价格。
- 客户议价不得自动突破底价／利润线；超出权限应转人工或请求审批。
- 演示版可使用模拟价格数据，但须清晰标注，避免被理解为正式企业报价。

## 5. 数据与对话管理原则

- **短期记忆**：读取最近若干轮完整对话，保证多轮咨询的连贯性。
- **长期记忆**：把较早对话沉淀为客户画像和摘要，只在需要时检索；避免全量历史进入模型造成成本和时延问题。
- **结构化沉淀**：至少记录客户需求、报价条件、报价版本、意向等级、异议、跟进状态和人工接管记录。
- **真实性边界**：当前演示可先用模拟企业、套餐与价格数据；进入真实客户场景前需补齐数据授权、保留期限与权限控制。

## 6. 产品目标与成功指标

### 6.1 P0 上线门槛

- 无有效规则时错误报价率为 0%；底价／利润线违规次数为 0。
- 服务端报价计算正确率、规则版本可追溯率均为 100%。
- 核心意图识别和关键字段提取准确率不低于 90%，缺失字段追问正确率不低于 95%。
- 用户意向等级准确率不低于 85%，证据可追溯率 100%，无证据推断率 0%，建议动作策略合规率 100%。
- 人工接管后 AI 误回复率为 0%。
- 首条可见响应 P95 不高于 3 秒，完整回复 P95 不高于 10 秒。
- 月度系统可用性目标不低于 99.5%。

### 6.2 P1 业务 KPI

- 首次回复自动完成率目标不低于 80%。
- 报价条件自动收集完成率目标不低于 60%。
- 有效留资率相对基线提升不低于 15%。
- 预约量房转化率相对基线提升不低于 10%。
- 单线索人工处理时长相对基线下降不低于 30%。
- 高意向客户按时跟进覆盖率不低于 95%，完整回访任务比例不低于 98%。

没有历史基线时，生产灰度前两周作为基线观察期。每项 KPI 必须记录负责人、数据来源、统计周期、排除条件和看板口径。

## 7. 实现前仍需由企业补充的真实数据

1. 真实服务城市、核心／灰度／不承接行政区及区域附加费。
2. 材料、设计师、施工、拆改、水电等真实单价、公式、最低价与有效期。
3. 成本和最低利润线、销售折扣权限、不可叠加规则与报价审批人。
4. 公司资质、案例、售后和服务话术的已批准版本。
5. 客户数据保留、删除、导出和访问权限政策，以及隐私责任人。
6. KPI 负责人和企业现有业务基线；没有基线时按第 6 节启动观察期。

## 8. 建议的下一步

1. 按《装修销售 AI 知识库内容需求索引》的 P0 模板录入默认边界与样例报价数据。
2. 完成知识内容到候选规则、校验、审批和 RDS 规则版本发布的闭环设计。
3. 用不少于 30 组标准对话验证意图、字段、知识召回、报价和人工兜底。
4. P0 达到第 6.1 节门槛后，再实施 P1 实时工作台、意向分析与回访能力。
5. 灰度上线后收集两周业务基线，确认 P1 KPI 的正式目标。
