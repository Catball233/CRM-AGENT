## 1. 审查结论

| 项目 | 结论 |
| --- | --- |
| 审查对象 | 本地 MVP 的 HTTP API、SSE 事件、公共数据类型和模块接口 |
| 审查基线 | PRD、知识库规范、验收策略、解决方案设计、项目执行计划 |
| 审查轮次 | 5 轮 |

审查结束后形成的规范见[接口契约 v1.0](../specs/接口契约-v1.0.md)。本记录只保存评审过程，不作为运行时定义来源。

## 2. 第一轮：业务链路完整性

审查问题：接口是否覆盖 PRD 中完整的本地用户路径和内部业务路径。

| 发现 | 风险 | 处理结果 |
| --- | --- | --- |
| 只有零散 JSON 示例，没有创建、恢复、清空会话接口 | 前端无法独立对接 | 增加会话创建、快照读取和本地清空接口 |
| 没有统一的 turn 结果 | 回答、追问、报价和安全停止难以区分 | 定义 `ChatTurnResult.outcome` 判别联合 |
| 规则导入与激活没有模块契约 | C 模块无法与编排和 SQLite 解耦 | 定义 `RuleImportService` 与 `RuleImportBundle` |
| 知识不足、字段不足和规则冲突未形成统一结果 | 容易把正常业务停止误当系统异常 | 定义 `QuoteUnavailable`，与 HTTP 错误分离 |
| 验收需要查看分析和证据，但没有读取接口 | 难以验证意图、记忆和知识链路 | 增加仅限 local/test 的只读调试快照接口 |

第一轮结论：通过修正。

## 3. 第二轮：类型、语义和状态一致性

审查问题：同一字段在 PRD、前端、AI、知识、记忆和报价模块中是否含义唯一。

| 发现 | 风险 | 处理结果 |
| --- | --- | --- |
| `intent: interested` 把意图类型与价值等级混用 | 训练样例和代码枚举不一致 | `intent` 只表示消息目的；购买价值统一放入 `value_assessment.level` |
| `extracted_slots: {}` 不含确认状态和来源 | 推断事实可能冒充确认事实 | 改为 `SlotUpdate[]`，包含状态、置信度和来源引用 |
| `ContextBundle` 使用无来源对象 | 无法证明追忆正确或隔离会话 | 事实、摘要和召回项均使用带 ID/来源/时间的结构 |
| `ChatEvent.payload` 为任意对象 | 前后端可各自解释字段 | 定义带 `event_type` 的判别事件联合、序号和终止规则 |
| 报价结果缺少币种、父报价和证据 | 重做和对账不可追溯 | 增加 `currency`、`parent_quote_id`、规则引用和知识证据 ID |
| 类型没有版本 | 四人并行时无法判断兼容性 | 所有跨模块顶层对象加入 `contract_version` |

第二轮结论：通过修正。

## 4. 第三轮：错误、幂等、并发与恢复

审查问题：重复提交、调用失败、SSE 断开和应用重启是否产生确定行为。

| 发现 | 风险 | 处理结果 |
| --- | --- | --- |
| 只规定 `client_message_id` 唯一，未规定重复时返回什么 | 双击可能出现不一致 UI | 同 ID 同内容按状态回放、返回处理中或允许显式重试；同 ID 异内容返回 409 |
| 没有失败 turn 的重试契约 | 前端可能重复创建客户消息 | 增加基于原 turn 的重试接口，新建 attempt，不重复保存客户消息 |
| 同会话串行只写在说明中 | 各模块可能并行写记忆和报价 | 定义 `CONVERSATION_BUSY` 与 turn 状态机 |
| SSE 没有事件序号和终止条件 | 断线后难判断是否完成 | 每个事件包含递增 `sequence`；每个 turn 只能有一个终止事件 |
| 外部调用和 SQLite 事务边界不清晰 | 长事务或部分报价可能残留 | 外部调用不持有事务；最终数据在单一完成事务中提交 |
| HTTP 错误和业务不可报价混在一起 | 前端错误处理不稳定 | 定义统一 `ApiError`、错误码和 `retryable`；正常不可报价进入 turn 结果 |

第三轮结论：通过修正。

## 5. 第四轮：安全与数据边界

审查问题：接口是否会扩大本地 MVP 权限、泄露敏感数据或造成跨会话污染。

| 发现 | 风险 | 处理结果 |
| --- | --- | --- |
| 调试数据可能暴露提示词和供应商原始响应 | 本地演示也可能泄密 | 调试接口禁止返回 API Key、系统提示词、思维链和未脱敏响应 |
| 外部模型输入范围未限定 | 可能发送无关历史或本地数据 | 只发送当前消息和经过构建的 `ContextBundle`；不发送 SQLite 文件或密钥 |
| 知识切片可能包含指令性文本 | 提示词注入可能改变规则 | 知识证据按不可信数据处理，不赋予工具、写库或规则激活权限 |
| 模型和前端写入规则的边界不明确 | 可绕过权威报价 | 规则导入、激活和报价只通过 NestJS 内部服务；模型仅给分析与文本建议 |
| 会话隔离依赖实现自觉 | 可能召回其他测试会话 | 所有 Repository 查询强制带 `conversation_id`，跨会话读取为契约违规 |
| 错误日志缺少脱敏要求 | 可能记录密钥或真实 PII | 统一规定日志脱敏和测试数据限制 |

第四轮结论：通过修正。

## 6. 第五轮：可测试、可模拟与团队集成

审查问题：A/B/C/D 是否能独立实现并通过假依赖拼接。

| 发现 | 风险 | 处理结果 |
| --- | --- | --- |
| 模块方法签名未冻结 | 假实现和真实实现无法互换 | 定义 AI、知识、记忆、报价、规则导入和 Repository 接口 |
| 没有契约样例的唯一位置 | 四人会复制并修改 JSON | 指定 `packages/contracts` 为定义源，`packages/test-fixtures` 为样例源 |
| Schema 只在模型出口校验 | HTTP、SSE 或 Repository 边界仍可能污染 | 要求所有跨模块输入输出进行运行时 Schema 校验 |
| 12 个场景未映射接口 | 验收不能定位失败层 | 建立 S01–S12 与类型、事件、错误码的映射表 |
| 契约变更规则不足 | 并行开发容易静默破坏兼容 | 采用语义化版本；破坏性修改升主版本并由 A 和受影响负责人批准 |

第五轮结论：通过修正。
