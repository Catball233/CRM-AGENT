# 装修销售 AI｜四人本地 MVP 执行计划

## 1. 四人角色与代码所有权

4 人全部参与编程，采用模块负责人制，并共同承担集成与验收。

| 人员 | 主要角色 | 编程任务 | 集成责任 | 主要评审人 |
| --- | --- | --- | --- | --- |
| A | 技术负责人／集成负责人 | 单仓库、公共契约、NestJS 骨架、会话编排、API、幂等、错误处理和最终集成 | 管理主分支、冻结接口、协调 SQLite 迁移顺序和端到端链路 | B/C/D 按模块评审 |
| B | AI 与记忆负责人 | 百炼模型适配、意图识别、客户价值判断、上下文构建、短期记忆、长期记忆和 Schema 校验 | 保证 AI/记忆输出符合公共契约，可用假仓储独立测试 | A；C 复核数据接口 |
| C | 知识、报价与数据负责人 | 百炼知识检索、SQLite Schema/迁移、规则导入与激活、报价计算、报价版本和数据仓储 | 维护数据库结构、规则测试样例、报价对账和仓储接口 | A；B 复核 AI/规则接口 |
| D | 前端与质量负责人 | Next.js 聊天页、SSE/完整响应展示、会话恢复、报价卡片、错误状态、模拟 API 和端到端测试 | 使用公共契约对接 API，维护完整用户流程回归 | A；B/C 复核对应输出 |

A 是技术决策和集成责任人，但不替代其他成员编码。B/C/D 的模块必须能在真实集成前通过假依赖独立运行。

## 2. 模块解耦方案

### 2.1 可并行完成

| 模块 | 负责人 | 独立输入 | 独立输出 | 可用假依赖 |
| --- | --- | --- | --- | --- |
| 聊天页与报价卡片 | D | 模拟 `ChatEvent` | 页面状态和交互 | 模拟 API、固定报价 JSON |
| 意图与价值判断 | B | 消息 + `ContextBundle` | `AnalysisResult` | 固定上下文、假模型响应 |
| 短期/长期记忆 | B | 会话消息和事实事件 | `ContextBundle`、记忆更新 | 内存仓储或假 Repository |
| 知识检索适配 | C | 查询 + 上下文 | `KnowledgeEvidence[]` | 固定知识结果 |
| SQLite 仓储 | C | Repository 输入 | 持久化实体 | 临时 SQLite 测试库 |
| 规则导入与激活 | C | Markdown/CSV/JSON 样例 | 激活规则版本 | 固定规则文件 |
| 报价计算器 | C | `QuoteRequest` + 激活规则 | `QuoteResult` | 内存规则仓储 |
| 会话编排 | A | 公共接口 | `ChatEvent[]` | FakeModel/FakeKnowledge/FakeMemory/FakeQuote |
| 端到端测试 | D | 标准场景与运行应用 | 通过/失败证据 | 先对模拟 API，后对真实 API |

### 2.2 必须统一控制

- `packages/contracts` 中的公共 Schema、事件和错误码；
- 会话状态机和消息处理顺序；
- SQLite Schema、迁移编号和种子入口；
- 金额单位、时间格式、日志字段和 ID 规则；
- 主分支集成、依赖版本和统一启动命令；
- 端到端完成定义。

## 3. 公共契约冻结清单

G0 前四人共同确认；字段、接口和错误行为以[接口契约 v1.0](specs/接口契约-v1.0.md)为准：

- `AnalysisResult`；
- `ContextBundle`；
- `KnowledgeEvidence`；
- `QuoteRequest`、`QuoteResult`；
- `ChatEvent`；
- `ApiError`；
- 会话状态枚举；
- 确认事实、推断事实和冲突事实的数据结构；
- 金额统一使用整数分；
- 时间统一使用 ISO 8601，数据库保存统一时区。

公共契约修改流程：提出变更 → A 判断影响 → 受影响负责人评审 → 先合并契约 → 各模块适配。不得在模块内部复制并改名。

| M1 模块可独立运行 | 第 1 周 | B AI/记忆、C 知识/报价/SQLite、D 前端模拟、A 编排假实现 | A/B/C/D | G1、G2 |

## 5. 工作节奏

- 每日 10 分钟同步：已完成、今日接口、阻塞项。
- 每天至少一次把短分支同步到 `main`，禁止一周后集中合并。
- 每两天进行一次 30 分钟集成走查，用真实主分支运行核心链路。
- 公共契约、迁移和状态机变更必须提前通知，不得在合并时突然出现。
- 每个里程碑结束执行对应门禁，不以口头“基本完成”替代证据。

## 7. 代码一致性规则

### 7.1 仓库与工具

- 一个单仓库、一个包管理器、一个锁文件。
- 一套根 TypeScript、格式化、静态检查和测试配置。
- `main` 始终保持可安装、可迁移、可启动和可运行基础测试。
- `.env`、个人 SQLite 文件和真实密钥不得提交。

### 7.2 分支与评审

```text
feature/a-orchestrator
feature/b-ai-memory
feature/c-knowledge-quote
feature/d-chat-ui
```

- 分支尽量不超过两天。
- 每个变更只解决一个任务 ID。
- 公共 Schema：A + 受影响模块负责人批准。
- SQLite 迁移：C 创建，A 复核；已合并迁移不得重写。
- AI/记忆：B 主责，A 或 C 评审。
- 知识/报价：C 主责，A 和 B 至少一人评审。
- 前端/E2E：D 主责，A 或对应输出负责人评审。

### 7.3 统一约定

- 金额使用整数分。
- 时间使用 ISO 8601；数据库保存统一时区。
- ID、错误码、日志字段和状态枚举来自公共包。
- 提示词、Schema、规则和记忆摘要均有版本号。
- AI、知识、报价、仓储只通过接口协作，不跨模块直接访问内部实现。

## 8. SQLite 协作规则

每名成员使用自己的本地数据库，例如：

```text
data/dev-a.sqlite
data/dev-b.sqlite
data/dev-c.sqlite
data/dev-d.sqlite
```

这些文件不提交仓库。仓库只提交：

- 迁移文件；
- 初始化/种子数据；
- 脱敏知识和规则样例；
- 标准场景和预期结果。

任何人不得通过共享一个运行中的 SQLite 文件协作。数据一致性靠迁移、种子和公共契约保证。

## 9. 完成定义

任务只有同时满足以下条件才算完成：

- 代码合并到主分支；
- 类型、格式和静态检查通过；
- 正常、缺失和失败用例通过；
- 公共契约未被私自复制或破坏；
- 数据库变更包含迁移和测试；
- 没有提交密钥、真实 PII 或个人 SQLite 文件；
- 主分支仍可从空库启动；
- 对应负责人之外至少一人完成评审。

每周监测：

| 指标 | 说明 |

## 11. Post-MVP 候选池

- SQLite 迁移 PostgreSQL/RDS；
- 公网部署、HTTPS、限流和监控；
- 销售账号、人工接管、Redis、WebSocket 和回访；
- 真实客户 PII、隐私政策和业务 KPI；
- 多实例、高可用和灾备。

当前不采用甘特图。4 人使用里程碑表、任务看板和门禁清单；只有在 Post-MVP 扩大团队或引入跨团队依赖时再增加甘特图。
